# Sigil context

Sigil (formerly Patina, Basalt and Cinnabar; the repository is still called vermillion) is a mobile-first monorepo for an app with personal accounts: a native app (Expo), an API server (Hono and oRPC on Dokploy, at `sigil-api.<domain>`). The old public site and admin UI were removed from the workspace for a rebuild; the API and its contract with the existing site remain.

## Glossary

- **App config** — `app.config.ts`, the single source of the app's name, base domain (every public host derives from it), ports, bundle ids, scheme and versions. Files that cannot import it (compose names, the server Dockerfile port, EAS URLs) are edited by hand.
- **Vertical** — a self-contained slice of domain code (`account`, `preferences`, `auth`, `exercise`) with procedures, operations, tables and a public `index.ts`. Other verticals may import it only through that index. The native modules mirror the shape. Deleting a feature is deleting its vertical.
- **Platform** — shared infrastructure inside an app or `packages/api`: database startup, HTTP middleware, the oRPC base, rate limiting, jobs, health. Importable from every vertical; not a vertical.
- **Operation** — one file in a vertical doing one thing (create a Custom exercise, delete an account). Procedures call operations.
- **Procedure** — an oRPC endpoint built from the `public` or `authed` builder.
- **`authed` seam** — the single builder that resolves the signed-in user.
- **Module hook** — the only way a component reads or writes app data (`use-exercise-library`, `use-preferences`). The sync layer sits behind the hooks, not in the components.
- **Reference vertical** — `exercise` is the first real vertical and the worked example of a synced table: a Reference-data catalog plus per-user Custom exercises, retire-never-delete, an upload handler, a client schema and seam 1 and 3 tests ([ADR 0034](docs/adr/0034-exercise-library.md)). The earlier `notes` example was removed ([ADR 0035](docs/adr/0035-remove-notes-example.md)); its tables stay in Postgres unused.
- **User preferences** — one row per user, created on first write: `locale`, `timezone` and a `ui` jsonb with defaults. A missing row means defaults. Theme is not a preference: it is stored per device ([native themes](docs/guides/native-themes.md)).
- **Locale resolution** — saved preference, then locale cookie, then `Accept-Language` (device locale on native), then `en`.
- **Registration policy** — `REGISTRATION_OPEN`. True: anyone may sign up (development). False: invite-only, the closed beta; existing accounts and `ADMIN_EMAILS` addresses still sign in.
- **Invite** — an `access_invite` row in state `invited` with a 14-day expiry. The address is the gate, not a code: a new account may be created only by an address with a live invite, by email code or Google. Redeemed once by the account it created. `expired` is derived, never stored.
- **Access request** — an address asking to join the beta from the site's form (rate limited, always the same answer); an `access_invite` row in state `requested` until the admin approves it.
- **Admin** — the owner, an address in `ADMIN_EMAILS` whose session has passed the authenticator (TOTP) step. The `role` column only caches the list. Every admin write leaves one `admin_audit` row. The admin sees no training data.
- **Minimum supported version** — the `minimum_app_version` setting; builds below it show a blocking update screen. Builds below the latest GitHub release see a dismissible notice.
- **Disposable email** — an address on a domain from the maintained `disposable-email-domains` list (parent domains included). Rejected when a sign-in code is requested and at email change.
- **Sign-in code** — the 6-digit one-time code emailed to an address; the only non-social way in. Valid 5 minutes, hashed at rest, 3 guesses, a resend replaces it. Redeeming it creates the account on first use.
- **Onboarding step** — a question during account setup after sign-in. The name is required when the profile is missing it. Native also offers setup questions and stores progress and completion per account on the device.
- **Trusted proxies** — the CIDRs (`TRUSTED_PROXIES`: Traefik and Cloudflare) from which the server accepts `X-Forwarded-For` when resolving the client IP.
- **Trusted origin** — the API's own origin (`APP_URL`) plus the site's origin (its Worker forwards `/rpc` and `/api`); state-changing browser requests from any other `Origin` are rejected. Native requests carry no `Origin` and bring their own credentials.
- **Job** — a Postgres-backed (pg-boss) unit of background work run inside the server process. Defined by queue name, zod payload (ids only), handler and retry settings.
- **Device owner** — the local identity (user id) a device's synced database belongs to. Not server authorization. Credentials and uploads for any other user are refused. Lives in `tests/sync`; round-trip tests land in later sync phases ([0021](docs/adr/0021-device-owner-and-account-lifecycle.md)).
- **Rejected write** — an upload the server permanently refused. Kept in the local-only `rejected_writes` table with its payload so the user can review, retry or discard it. Lives in `tests/sync`; round-trip tests land in later sync phases ([0018](docs/adr/0018-upload-protocol.md)).
- **Sync stream** — a PowerSync Sync Streams definition that selects which Postgres rows replicate to a user's device, filtered by `user_id`. Lives in `tests/sync`; round-trip tests land in later sync phases ([0015](docs/adr/0015-powersync-self-hosted.md)).
- **Bootstrap (sync)** — the idempotent admin job that creates the replication role, storage database and empty publication before PowerSync starts. Lives in `tests/sync`; round-trip tests land in later sync phases ([0023](docs/adr/0023-replication-setup.md)).
- **Seam 3** — the sync test seam: headless `@powersync/node` clients against `powersync-service`, the server and Postgres, run by `pnpm test:sync`. Lives in `tests/sync`; round-trip tests land in later sync phases ([0024](docs/adr/0024-test-strategy.md)).
- **Reference data** — rows identical for every user and written only by the server (today: the exercise catalog, `exercise.user_id IS NULL`). Read-only on devices; retired, never deleted ([0034](docs/adr/0034-exercise-library.md)).
- **Exercise catalog** — the Reference data exercises, maintained in the admin and synced by a global stream. The database is the source of truth.
- **Seed** — the committed catalog file (`packages/api/src/exercise/data/exercises.json`), inserted only into an empty table on start; the admin's export reproduces it.
- **Custom exercise** — an `exercise` row owned by a user. Archived and restored, never deleted; its type is fixed once a set uses it.
- **Muscle group** — one of 20 code-defined slugs an exercise targets (one primary, any secondary). The body map draws 17 of them. Some groups have Muscle details.
- **Muscle detail** — a finer part of exactly one Muscle group (23 code-defined slugs, for example `rear_delts` in shoulders), stored next to the groups as optional `primary_detail` and `secondary_detail`. Groups stay what everything reads; a row without details behaves as a group-only row. Clients drop slugs they do not know ([0050](docs/adr/0050-muscle-details-and-catalog-expansion.md)).
- **Catalog patch** — a committed, ordered, validated file of changes to Reference data, applied once (fingerprinted per file in `reference_import`): it inserts catalog rows and fills empty fields, never deletes or overwrites a value the admin may have set. A deliberate change carries the value it expects to replace and is skipped if the row differs. It may wait for `minimum_app_version` ([0050](docs/adr/0050-muscle-details-and-catalog-expansion.md)).
- **Program** — a plan followed over weeks: an ordered Rotation of Workouts and rest days, with an optional planned length in weeks, an optional Session goal and an optional cover photo. Owns its Workouts.
- **Workout** — a plan for one training day ("Push A"): an ordered list of exercises, each with Planned sets, a rest time and a Pinned exercise note, and an optional cover photo (a copy keeps it). Standalone, or owned by exactly one Program; adding a Workout to a Program copies it, never shares it. Not the record of training: that is a Session.
- **Session** — the record of actually training on a given day, optionally started from a Workout. Keeps what was done even if the Workout later changes or is deleted.
- **Week** — seven calendar days in the user's time zone, starting on the `weekStart` preference (Monday by default, or Sunday or Saturday). `weekRange` in `packages/shared` supplies that boundary for the Home week strip and weigh-in count, weekly totals and their change, History's calendar and groups, and weekly chart buckets. A Run week starts at the Run's first Session and counts seven-day blocks after subtracting whole paused local days.
- **Session goal** — the Sessions a week to aim for, shown on Home as "2 of 4 sessions". Use the active Program's Session goal if set, then the user's "Sessions per week" preference. Otherwise use the number of workout Slots in a Rotation with seven Slots or fewer, if it has any.
- **Rotation** — a Program's ordered cycle of slots (a Workout or a rest day). "Next up" follows the last Session from the Program, not the calendar, so a missed day never makes anything overdue.
- **Active program** — the one Program (or none) whose next Rotation slot is suggested. Any Workout can still be started at any time. A Program keeps its start and end dates once run.
- **Planned set** — a target inside a Workout: a Set kind, a rep range (min = max for a single number), and optionally a weight and an effort target. Other fields follow the exercise type.
- **Run** — one time through a Program, from its first Session to Finish. Pausing holds the Run's week and phase. Starting one of its Workouts resumes the Run and counts the Session in it. A backfill inside a pause stays outside the Run. Re-running a Program starts a new Run and keeps earlier Runs in history.
- **Completed Program** — a Program whose last Run is finished.
- **Slot** — one position in a Rotation: a Workout the Program owns, or Rest. One Workout may fill several Slots; editing it changes them all. Rest Slots are advisory: never marked, never blocking a Cycle.
- **Cycle** — one pass through a Rotation. A counted, finished Session marks its recorded Slot done and takes precedence over a skip on that Slot. Legacy Sessions without a Slot fill the first available Slot for their Workout. "Next up" is the first remaining Workout Slot. A Cycle completes when every Workout Slot is trained or skipped. A counted Session in a later Cycle seals earlier Cycles. The UI stops offering Undo for their skips, though the server still accepts queued Undo for the original Run.
- **Skip this cycle** — leaves a Workout Slot out of one Cycle without changing the Rotation. The synced record has a deterministic id derived from Run, Slot and Cycle. Undo deletes that id. Skipping again reuses it.
- **Superset** — consecutive exercises in a Workout grouped to be done back to back; rest follows the last one. A circuit is a Superset of more than two.
- **Effort** — how hard a set is, one scale shown as RPE (6–10 in halves) or RIR (10 − RPE) by preference. A target may be a range.
- **Set kind** — warm-up, working, drop, failure, top, back-off or myo-reps. Partials and negatives are notes.
- **Pinned exercise note** — a note on an exercise within one Workout ("Smith machine, seat 4"), shown every time that Workout is trained.
- **Active session** — a Session not yet finished. One is expected per account; duplicates from offline starts are shown to the user, never auto-deleted. Owned by one device at a time ([0038](docs/adr/0038-sessions.md)).
- **Logged set** — one performed set in a Session: its kind, actual values, optional effort, completion time and a snapshot of its Planned set. Written as its own row.
- **Tick** — completing a Logged set. Ticking fills empty cells from Ghost values; a set with a required field and no value or Ghost cannot be ticked, so an invalid completed set never exists. Unticked sets are dropped at Finish.
- **Previous** — the matching set by kind and position from the latest finished Session of the same Workout by default. Fixed-rep progressing sets can use one whole Session entry with the same set kinds, counts, reps, effort and planned loads from any Workout. With no same-Workout history, Previous can use another Workout.
- **Ghost value** — the muted suggestion in an empty set cell: Previous, else the planned target (reps: Previous only when inside the planned range).
- **Prescription snapshot** — what a Session exercise was suggested, per set: load, reps, effort, the reason and its factors, the Session gym and what each target was, stored on the Session exercise (`session_exercise.prescription`, synced, private to the user). The owning device captures it the first time the targets are shown or used, so later history, phase or gym changes do not move the numbers under the lifter. A re-suggestion names the snapshot it replaces. It is revised only for the unticked sets, when the Session gym moves, a set's kind or target is edited or a set is added; a build that cannot fully read one never revises it.
- **Prescription** — what the engine asks of one exercise for the next Session: per set a load, reps (or a time or distance), a reason with its numbers, and the evidence behind it. `prescribe()` in `packages/shared` is the one entry point; the Session, the live notification, the Workout preview, the exercise page and Home's stall nudge all ask it, so they agree. A Session's own Prescription snapshot, once captured, is read back instead.
- **Progression rule** — how an exercise's load and reps move, stored on its exercise setting (none is Double). Double: reps climb to the top of the range, then load. Linear: fixed reps, load added each Session every set was made; a miss holds, the second miss in a row at a load takes off 10%. Top set and back-offs: the top set moves like Double and the back-offs stay a share of it (the rule's percent, else last time's, else 90%). Maintain: loads and reps repeat and the lift is never reported as stalled. A break or Deload still lowers any of them; planks and carries add time, distance or load whatever rule is named.
- **Evidence** — what a suggestion rests on, kept in the Prescription snapshot: the Session it was read from (date and the progressing sets compared), the factor that scaled the load (a break with its days, or a Deload) and where the grid or a cap moved a load. The reason sheet shows it in one or two lines.
- **Same-day adjustment** — after a working, top or back-off set misses its target (2 reps, 1.5 effort, or 1.5 reps of capacity when both are logged) or beats it by the same, the unticked progressing sets of that exercise move one step with a one-line reason ("Lighter: set 1 was 3 reps short."). At a load other than the suggested one the set is judged by estimated 1RM, so adding weight is not a miss. Each set triggers once; ticked sets, warm-up, drop, myo and failure sets and other exercises never move; a Lighter week or Deload never raises; Undo takes back the newest adjustment, and unticking the trigger set takes back its own.
- **Override prompt** — one quiet question after the same override twice: the step the lifter keeps taking at a gym, or the reps they keep doing above the planned range of a Workout exercise (judged over the whole exercise). Answering writes the gym exercise setting or the Workout's rep range for the sets on exactly that range; dismissals are kept in a bounded preference list, longest.
- **Take over** — moving an Active session to this device; the other device becomes read-only for it.
- **Record** — an exercise best (heaviest weight, estimated 1RM, which counts the reps left in reserve (10 minus RPE, at most 4, up to 12 in all) when effort is logged, best set volume, best session volume, rep records 1–12, longest duration/distance, best pace). Computed from Logged sets when read, warm-ups excluded.
- **Counted set** — any Logged set except a warm-up. Volume, set counts, Records and muscle distribution use only Counted sets.
- **Muscle distribution** — Counted sets per muscle group: 1 for the exercise's primary muscle, 0.5 for each secondary. Within a group a set's share is split equally across the exercise's details of that group (the rest is unspecified), so the breakdown adds up to the group total.
- **Muscle volume** — Counted sets per muscle over a Week: 1 for the primary muscle, 0.5 for each secondary ([0044](docs/adr/0044-muscle-volume-and-stalls.md)).
- **Muscle goal** — a weekly set range per targeted muscle: Maintain 6–10, Grow 10–20 (default), Focus 16–24 or Custom. Stored in the `ui` preferences as `muscleGoals`. Status is below, on target or above.
- **Training break** — time since the latest Session with a completed working, top or back-off set for the exercise, across Workouts and gyms. A gap of at least 14 days between counted Run Sessions turns the returning Test week into Build.
- **Stalled lift** — a lift with three baseline Sessions and no gain over the Session before them. A gain is more load at the prescribed minimum reps, more reps at the same load or at least 1% higher estimated 1RM, compared within each set kind. A break of 14 days ends the comparison. Three Sessions in a row that missed their suggestion without gaining also show a note, but ask to hold or review the target and never offer the deload.
- **Stall deload** — an accepted lighter target for one exercise entry in a Session. The entry starts a new stall episode. Only later baselines can count toward the next stall.
- **Lighter week** — the older form of a Deload. For seven days the engine suggests 90% of the last load and makes about half the planned sets optional. Those Sessions stay out of progression and stall baselines. Home offers "Insert deload week" while a Run is active and offers a Lighter week when there is no Run.
- **Phase** — what a Run week asks of a Workout. Build follows the plan, Push adds 1 RPE, Test gives the main lift one top set and halves the accessory sets, and Deload defaults to half the sets rounded up, 2 RPE lower and 90% of the load. A Test single aims for RPE 8–9 at about 90–95% of estimated 1RM before break and equipment adjustments. A Deload rounds down within five percentage points of the intended cut and otherwise uses the nearest load. Test and Deload Sessions stay out of progression and stall baselines. A Session keeps its phase (`training_session.phase`) and modifier snapshot (`phase_modifiers`) when it starts.
- **Phase plan** — a Program's repeating Phase pattern, per-week overrides, modifier edits and Test settings. Test can include two lighter work-up singles. A Program with no Phase plan has no scheduled phases.
- **Inserted deload** — "Insert deload now" replaces the next scheduled Deload within one pattern length, or replaces just the current Run week if there is none. Replacing a scheduled Deload restarts the pattern the following week. The planned Run length stays the same. A Program with no pattern follows Build around the insert.
- **Main lift** — the Workout exercise a Test week turns into one top set: `workout.main_entry_id`, else the Workout's first exercise.
- **Gym equipment** — a Gym's bars and plates (seeded kit plus custom items, with plate counts) used by the plate calculator. Not part of the exercise equipment taxonomy.
- **Gym** — a place the user trains, with its own kit (Gym equipment) and its own say about each exercise: a Max load, a Load step and a setup note (the Gym exercise setting, one per Gym and exercise). The server creates "My gym"; the last Gym cannot be deleted. With one Gym nothing about Gyms shows.
- **Equipment here** — the equipment types a Gym has (`gym.unavailable_equipment` lists the ones it lacks; empty means all, and bodyweight is always there) and its optional Dumbbell max. Swaps list exercises the Gym has first and mute the rest as "Not here"; the exercise library can hide them with "Available here". Nothing is ever blocked.
- **Dumbbell max** — the heaviest dumbbell a Gym owns (`gym.dumbbell_max_kg`, per hand). It caps every dumbbell exercise there; an exercise's own Max load still wins when it is lower.
- **Active gym** — the Gym the user trains at now (`ui.activeGymId`; an unknown id reads as the oldest Gym). It governs everything outside a Session: the exercise page, the kit screens and the progression preview.
- **Session gym** — the Gym a Session was trained at (`training_session.gym_id`, set from the active gym when it starts, changeable in the Session). During a Session the Max load, Load step, setup note, plate calculator kit and cap, warm-up rounding and the live notification's Ghost values all follow the Session gym, not the active gym. A Session with no Gym (an older Session, "Any gym", or a Gym that was deleted) falls back to the active gym for those. Its history is the exception: no Session gym reads the Sessions of every Gym.
- **Load grid** — the loads a Gym can make for an exercise: its own ranges when it set a Load step, else the loaded bar and plates of a barbell (the exercise's remembered bar when this Gym has it, else the Gym's default bar), else the usual dumbbell rack; machines and cables have none. A Max load set without a step only caps whichever of those applies, and a manual weight increment still wins over the kit and the defaults, though not over a Gym's own step.
- **Replay identity** — the durable identity (account, install, transaction, request digest) an upload carries so the server returns the same outcome after a lost response instead of re-applying it ([0018](docs/adr/0018-upload-protocol.md)).
- **Seam 1** — the API router called in-process against a clone of a migrated template database on the Docker Postgres. There is no browser seam; the site's Worker routing and admin gate are unit tested.
- **Origin** — the Dokploy server (Traefik, then the server container) behind the proxied `sigil-api.<domain>` record. Firewalled to Cloudflare's IP ranges.
- **Brand tokens** — `packages/ui/src/tokens/brand.ts`, the one place colors, radius and fonts are defined; mapped to native by generated CSS and read directly by the email templates.
- **Theme** — the native app's colour scheme: a mode (System, Light or Dark) and an accent, colour-only, never layout. Dark is AMOLED black and Light is pure white, as in email.
- **Theme setting** — Settings → Appearance, which sets `device.theme` (`{ appearance: "system" | "light" | "dark", accent }`). System follows the OS; Light and Dark force the colour scheme for native chrome.
- **Accent** — Lime (default), Gold, Ember, Rose, Ice or Mono: the only hue in the interface, with `action` / `on-action` roles for the fill and the label on it. It marks the primary action, the current and completed sets, records, the selected tab and chips, and the primary chart series. Red (`danger`) is the only status colour.
- **Media** — a user's uploaded image: a synced `media` row (made on the device) plus a full-size and a thumbnail object in the private user bucket. Rows point at media, never the reverse. Files reach R2 through presigned URLs and PowerSync's attachment queue ([0040](docs/adr/0040-user-media.md)).
- **Media reference** — the column or child row that says where Media shows: `program.cover_media_id`, `workout.cover_media_id`, `exercise.image_media_id`, `ui.avatarMediaId`, `session_photo`, `progress_photo`.
- **Catalog media** — exercise thumbnails and videos in the public bucket, named by keys on catalog rows and written only by the server or the admin site.
- **Body measurement** — one value of one body metric (weight in kg or a tape site in cm) at a moment, with the user's `local_date` ([0041](docs/adr/0041-body-metrics.md)).
- **Scale weight** — what the scale said: the logged weight entries (averaged per day).
- **Trend weight** — the smoothed weight: an exponential moving average (α 0.1) over daily scale weight with gaps interpolated. Computed on read; the number the app leads with.
- **Tracked metric** — a tape site the user chose to measure; only tracked metrics show in Check-in and on the Measurements page.
- **Check-in** — everything logged on one `local_date`: measurements, weight and progress photos. Not stored as its own row.
- **Progress photo** — a front, side or back body photo on a date; Media of kind `progress_photo`, blurred in lists while Hide photos is on.
- **Share card** — a 1080 × 1920 image of a Session, Workout or Program in the user's Theme, saved to Photos or sent through the system sheet. The only way to share; text share was removed ([0042](docs/adr/0042-share-cards.md)).
- **Template** — one card layout for a kind: Session Summary, Muscles and Photo; the Workout card; Program Overview plus one card per Rotation slot.
- **Sticker** — a Session's stats block alone as a transparent PNG, to lay over the user's own photo in a story.
- **Share composer** — the full-screen route that previews a Share card and picks its Template, background and privacy toggles, remembered per kind on the device.
- **Share link** — a short URL (`/p/<code>` for a Program, `/w/<code>` for a Workout) to a Snapshot. Opens in the app through Android App Links, or a web preview. Needs sign-in to make; the owner can revoke it ([0058](docs/adr/0058-share-links.md)).
- **Snapshot** — the immutable, versioned JSON copy of a Program or Workout a Share link serves (`sigil.program/v1`, `sigil.workout/v1`). A finished Session becomes a Workout Snapshot (a template), never history.
- **Code** — the 6 characters of a Share link, from an alphabet without 0, O, 1, I and L; typed into "Enter code".
